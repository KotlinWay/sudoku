## Signing decision gate

On 2026-08-28, the local PKCS#12 alias `sudoku` was opened through ignored local
configuration. Its subject and SHA-256 fingerprint match the published RuStore
1.3 certificate character-for-character. Gradle `signingReport` independently
confirmed that the release signing configuration uses the same certificate.

The verified recovery copy is stored outside the repository at:

```text
%USERPROFILE%\.android\release-keys\info.javaway.sudoku\app-signing-key.p12
```

The repository copy named `keystore` was removed from the working tree and from
the tracked branch tip. Local `keystore.properties` points to the recovery copy
and remains ignored. The public fingerprint is safe to record; passwords and
private material are not recorded here.

Use this existing key as the Play app signing key and create a separate upload
key for routine uploads. Confirm the package-name ownership prompt when the app
is created in Play Console.

Do not generate or accept a different Play app signing key without explicit
owner approval: Android would treat builds from the two stores as different
signers and would not install one as an update over the other.

Residual risk: the encrypted PKCS#12 remains present in public Git history from
commit `857ec3571abb0c66a87bf64e133443a5648c9f34`. Rewriting public history or
rotating the production signing key requires separate owner approval and is not
part of this release change.

## Lint disposition

The release Lint checkpoint has zero errors. Two correctness warnings were
resolved for 1.4:

- `Integer.BYTES` was replaced with a byte-width calculation available on API
  23, and a one-complete-move boundary fixture now covers the save-file check.
- `BoardView` now has a narrow `ClickableViewAccessibility` suppression. This is
  intentional: the board exposes 81 separate virtual accessibility nodes, and
  each node implements `ACTION_CLICK`; a host-level `performClick()` cannot say
  which cell to activate. This follows Android's guidance to use a virtual view
  hierarchy when a custom view has distinct clickable regions.

The remaining 21 warnings stay visible (there is no baseline) and have these
release dispositions:

- 4 `InconsistentLayout`: landscape alone owns `tool_undo`, `tool_pause`,
  `tool_more`, and `level`. `GameActivity` binds the tools only after the
  `landscape` guard and checks the optional level view for null.
- 2 `NestedWeights` and 1 `UselessParent`: the landscape hierarchy is deliberate
  for the documented 592x320dp minimum geometry and the scrollable overlay.
  Refactoring it without profiling would put the already-smoke-tested compact
  layout at greater risk than the bounded extra measurement cost.
- 4 `Overdraw`: each root explicitly paints the same opaque `background` color
  as `AppTheme.windowBackground`. The warning represents one redundant solid
  fill, not layered translucent art; it is accepted for 1.4 to keep layout swaps
  visually deterministic.
- 1 `PluralsCandidate`: “%d left” and the Russian “Осталось: %d” do not change
  grammar with quantity, so a plural resource would duplicate identical text.
- 1 `UnusedAttribute`: `enableOnBackInvokedCallback` is intentionally consumed
  only on API 33+ and ignored on API 23-32, where the legacy Back path is tested.
- 7 `UnusedResources`: these dormant pencil labels/assets and the unused error
  color are absent from the optimized release APK, confirmed with `aapt2 dump
  resources`; their source cleanup is non-release work.
- 1 `AlwaysShowAction`: portrait keeps exactly the two primary in-game actions,
  Undo and Pause, visible; all secondary actions remain in overflow.

## Signing and package-registration decision

1. Preserve `28:B1:96:F4:09:75:71:BF:8C:F8:7F:44:4A:5C:6A:4B:11:E4:D2:E0:07:CD:90:88:37:75:BD:1A:75:90:38:D9`
   as the app signing identity in both stores.
2. During Play App Signing enrollment, choose the option to provide the existing
   app signing key and transfer it only through Play Console's official protected
   key-import flow.
3. Generate a separate upload key for routine Google Play uploads. Compromise of
   that upload key can then be recovered without changing the Android app signing
   identity.
4. If package-name registration asks for proof because the package already
   exists outside Google Play, sign the Play-provided verification APK with the
   existing app signing key.
5. Do not accept a Google-generated app signing key for this package. A build
   signed by a different key cannot update an installation from RuStore; Android
   would require uninstalling it first, which would discard this app's local game
   state and statistics.

These decisions preserve the current signing identity; they do not authorize key
rotation, public-history rewriting, or disclosure of private key material.
